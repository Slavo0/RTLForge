# Анализ: долгая загрузка `vsim.wlf` и лаги после загрузки

Дата замеров: 2026-11-13. Машина: 32 логических ядра, Windows 11, Python из `.venv`,
Questa 2024.1 `wlf2vcd.exe`. Код на момент замера: `863fdfe` + изменения удаления строк
(на загрузку и отрисовку не влияют).

## Что за файл

| Параметр | Значение |
|---|---|
| `vsim.wlf` | 465 МБ |
| VCD после `wlf2vcd` | **3.92 ГБ** (в 8.4 раза больше) |
| Сигналов в VCD | 237 (191 однобитный) + 7 собранных шин = 244 |
| Временных отметок (строк захвата) | **24 397 216** (шаг 10 нс, 0 … ~245 мс симуляции) |
| Изменений значений | ~514 млн (≈21 на отметку) |
| Самые «шумные» сигналы | `clk` записан **7 раз** под разными именами (`tb_top/clk`, `intf_fifo/clk`, `intf_ram/clk`, `dut.../clk`, `crc8.../clk`, `skid_buffer_rx/clk`, `skid_buffer_tx/clk`) — каждый меняется в каждой отметке; вместе это **33 % всех изменений**. Далее `timeout_ctr_ff[15:0]`, `crc_valid`, `tx_re` и его копии (~1.2 млн на 10 % файла каждый) |

## 1. Загрузка: куда уходит время

Полная загрузка ≈ **76 с + 232 с ≈ 5 мин 10 с**, две последовательные фазы:

| Фаза | Время | Доля |
|---|---|---|
| `wlf2vcd` → временный VCD 3.92 ГБ (52 МБ/с, однопоточно, внешняя утилита) | **75.9 с** | 25 % |
| Разбор VCD в `VcdCaptureReader.load` (Python, один поток) | **232 с** (≈102 тыс. отметок/с) | 75 % |
| Установка захвата в окно (`MainWindow.loaded`) | 0.3 с | ~0 % |

### 2‑минутный тест разбора с профайлером (cProfile, бюджет 120 с)

За 120 с под профайлером прочитано 10 % файла (2.56 млн отметок); без профайлера за
те же 120 с — 50 % (12.3 млн отметок). Распределение собственного времени:

| Где | Собств. время | Что это |
|---|---|---|
| `vcd.py` `load` — цикл по токенам | 30.9 с (26 %) | разбор каждого токена в Python: `token[0]`, проверки `in "01xXzZ"`, `by_id.get`, `rjust`, запись в `changes` |
| `data.py` `_Writer.append` | 23.7 с собств. / 43.1 с с вложенными (36 %) | 55.7 млн вызовов: сравнение с прошлым значением, `cache.get`, два `array.append` |
| `vcd.py` `SplitBusAssembler.append` | 14.6 с / 63.8 с с вложенными | раздача изменений по писателям, `value.lower()` (61 млн вызовов, 5.2 с), сборка шин из битов (`"".join`) |
| `dict.get` | 13.8 с | 163 млн обращений (`lookup`, `cache.get`, `affected.get`) |
| `array.append` | 10.6 с | 114 млн добавлений в индексы |
| `len`, `next`, `_tokens` | ~17 с | накладные расходы генератора токенов и проверок |
| Чтение файла и `str.split` | ~1.2 с | диск не узкое место |

Отдельный замер: **только** токенизация (без записи индексов) идёт 36 МБ/с, то есть
даже идеальный Python-цикл не прочитает 3.92 ГБ быстрее ~108 с. Узкое место — интерпретатор
на ~1 млрд токенов, а не диск и не numpy.

### Побочные затраты

- На диск во `%TEMP%` пишется временный VCD 3.92 ГБ, затем дисковые индексы
  ≈ 514 млн × 12 байт ≈ **6 ГБ** (оценка: `int64` start + `uint32` code на изменение).
- Прогресс до конца `wlf2vcd` не движется (75 с «висит» без процентов), потому что
  утилита не сообщает прогресс, а разбор начинается только после неё.

### Что даст выигрыш (по убыванию эффекта)

1. **Нативный или параллельный разбор VCD.** Python-цикл не опустится ниже ~2 мин на этом
   файле. Варианты: (а) пакетный читатель на Rust/C (кандидат уже записан в HANDOFF, п. 7);
   (б) разбиение VCD по отметкам `#t` на блоки и разбор в общем `WorkerPool` (31 процесс)
   с последующей склейкой: значение на границе блока берётся из конца предыдущего блока.
   Ожидаемо 232 с → 10–30 с.
2. **Кэш индексов рядом с WLF** (ключ: путь + размер + mtime). Повторное открытие того же
   WLF — секунды вместо 5 минут, без `wlf2vcd`. Это хранение данных захвата, а не
   настроек, поэтому сначала нужно ваше решение (AGENTS.md запрещает хранить состояние захвата).
3. **Конвейер `wlf2vcd` → разбор:** читать VCD, пока утилита его дописывает, — экономит до
   76 с. Требует проверки, что `wlf2vcd` пишет файл последовательно (не гадать).
4. Мелкие ускорения внутри цикла (`lower()` только для `X/Z`, без `dict` `changes` для
   одиночных изменений, локальные ссылки на методы): по профилю ~10–20 %, архитектуру
   не меняют.
5. Не писать копии `clk` в симуляторе (`log -r` только нужных сигналов) — треть изменений
   и треть объёма файла; это настройка симуляции, не программы.

## 2. Лаги после загрузки (даже в маленьком окне)

Замер — реальное окно `MainWindow` (offscreen) с полным захватом, `repaint()` области
диаграммы, лучшее из 5:

| Окно / строк на экране | Весь захват | 1 % захвата | 2000 отметок | 100 отметок |
|---|---|---|---|---|
| 800×500 / 7 строк | 138 мс | 210 мс | 203 мс | 140 мс |
| 1920×1080 / 19 строк | 248 мс | 413 мс | 334 мс | 218 мс |

Щелчок (перенос A), шаг масштаба и шаг прокрутки — каждый ≈ 210 мс (малое окно) /
≈ 420 мс (FHD): все они заканчиваются той же перерисовкой. Для сравнения, на
`vsim.vcd` из репозитория (1 млн отметок) та же перерисовка — 4–30 мс.
То есть время растёт с длиной захвата, а не с размером окна, — отсюда лаги в маленьком окне.

### Причина №1 (≈77 % кадра): `searchsorted` с дробными ключами

cProfile кадра «весь захват», FHD: 0.63 с из 0.82 с (3 кадра) — это `numpy.searchsorted`.
Индексы переходов `sig.starts` и `capture.times` — `int64` memmap, а позиция просмотра
`v.left`/`v.left + v.span` и границы пикселей — `float64`. При разных типах numpy
**приводит весь массив `starts` к float64** (копия всего memmap) на каждый вызов.
Для `clk` с 24 млн переходов это ~195 МБ на одну строку в каждом кадре.

Микротест на массиве 24 млн `int64`:

| Запрос | Время |
|---|---|
| 1921 ключ `float64` | 21.8 мс |
| 1921 ключ `int64` | 0.04 мс |
| один ключ `float` | 22.7 мс |
| один ключ `int` | 0.003 мс |

Места в коде, через которые это идёт в каждом кадре:

- `ila_viewer/rendering.py:173-174` — `sig.run_index(v.left)` и
  `searchsorted(sig.starts, v.left + v.span)` (float-скаляры) — по два на строку;
- `ila_viewer/rendering.py:189` — `searchsorted(sig.starts, edges)`, `edges` — float;
- `ila_viewer/data.py:71` `SignalData.run_index` — вызывается с float (`v.left`).

Исправление простое и не меняет результат: `starts` целые, поэтому
`searchsorted(starts, x, "right") == searchsorted(starts, floor(x), "right")`,
а для `"left"` — с `ceil(x)`. Ожидаемо кадр «весь захват» 248 → ~50 мс в FHD,
маленькое окно — десятки мс. Аналогичные вызовы с float-ключами стоит проверить в
`highlights.py`, `spi.py` (`window`/`busy`), `sampling.py`, `measurements.py`.

### Причина №2 (крупный план, 2000 отметок): `sample_x` поштучно

В режиме «рисуем каждый сегмент» `draw_segment` вызывает `v.sample_x` 2 раза на сегмент,
а каждый `sample_x` на VCD делает 3 обращения `time_offset_at` → `_time_parts` к memmap
`times` (по ~2–3 мкс). Профиль: 50 586 `sample_x` за 3 кадра = ~160 мс на кадр.
Решение: считать x для всех границ видимых сегментов одним векторным вызовом
(как уже сделано для `pixel_edges`), а начало координат (`origin`, `left`, `right`)
вычислять один раз за кадр.

### Причина №3 (меньше): повторные вычисления на строку

- `_time_edges(v)` (границы пикселей по времени) пересчитывается для **каждой** плотной
  строки, хотя одинаков для всего кадра — 19 раз за кадр в FHD.
- В плотном режиме цикл по пикселям на Python с поэлементным доступом к memmap
  (`indices[i]`, `sig.codes[...]`) — ~2 тыс. итераций на строку.
- `v.signal_color(sig)` и `QColor` создаются заново для каждого сегмента.

Что **не** является причиной: подсказка при движении мыши (0.1 мс), строка состояния,
установка захвата (0.3 с), рисование текста/линий Qt (единицы мс).

## Как воспроизвести

Скрипты замеров лежат в scratchpad этой сессии (не в репозитории): `profile_load.py`
(cProfile разбора с бюджетом 120 с), `noprof.py` (скорость без профайлера),
`vcd_stats.py` (структура VCD, скорость токенизации), `profile_render.py`
(перерисовка и обработчики окна на загруженном захвате). Конвертированный VCD:
`wlf2vcd vsim.wlf -o converted.vcd`.

## Итог: что исправлено (14.11.2026)

Работа шла по очереди задач `docs/WLF_PERF_TASKS.md`. Ниже числа замеров, отчёт
`python -m scripts.benchmark_wlf --file vsim.wlf --workers 0 --disk`, 15 процессов.

**Загрузка `vsim.wlf`: 346 с → 44–49 с.**

| Этап | Было | Стало | Что сделано |
|---|---:|---:|---|
| `wlf2vcd` | 83,4 с | 12,4–13,9 с | WLF делится по времени на 15 частей (`wlfman filter`), они преобразуются одновременно и склеиваются |
| Разбор VCD | 262,6 с | 31,5–34,5 с | тело VCD разбирается диапазонами на пуле процессов; шины из битов собираются после разбора |
| Проверка стыков | — | 0,045 с | значение каждого сигнала на каждом из 14 стыков сверяется с загруженным захватом |

Склейка частей проверена на Questa 2024.1 и сверяется при каждой загрузке:
- заголовки частей;
- время начала каждой части;
- значения всех сигналов на стыках.

При расхождении захват отбрасывается и файл загружается одним запуском `wlf2vcd`, о
чём сообщает строка состояния. Нарезку можно отключить в «Настройки → Источники».
На `vsim.wlf` захват по частям совпадает с захватом одного запуска полностью: 0
различий.

**Перерисовка (FHD): 223 мс → 7,0 мс для всего захвата, 204 → 37 мс при 1 %.**

| Причина | Исправление |
|---|---|
| №1: `searchsorted` с дробными ключами по int64 (≈77 % кадра) | `data.search_sorted` ищет целыми ключами без копирования массива |
| №2: `sample_x` поштучно | `ViewportTransform` строится один раз на кадр и пересчитывает массивы |
| №3: повторные вычисления на строку и сегмент | `RowPainter` берёт цвета, перья и подписи один раз на строку; плотные участки — `pixel_runs` массивами |

Время перерисовки всего захвата больше не растёт с длиной захвата: 4,7 мс при 250 тыс.
отметок и 5,0 мс при 4 млн. Проверка `--check-scaling` падает, если вернуть дробные
ключи (рост в 12,99 раза).

**Дополнительно:**
- преобразование WLF показывает ход;
- нехватка места на диске даёт понятное сообщение после полной очистки;
- временные папки, брошенные после сбоя, удаляются при следующем запуске.

**Осталось:**
- разбор сразу после преобразования медленнее, чем разбор VCD, записанного раньше
  (22 с против 17 с на этапе разбора); причина не исследовалась;
- память растёт с числом различных значений сигнала;
- кэш индексов рядом с WLF (задача 9) ждёт решения владельца.
